# Implementation Plan: More Photo Clutter

**Branch**: `015-more-photo-clutter` | **Date**: 2026-10-24 | **Spec**: [spec.md](spec.md)

**Input**: Feature specification from `/specs/015-more-photo-clutter/spec.md`

## Summary

Three new removal categories (Bursts, Dark, Screen Recordings) and one trim action (Keep Still
Only on Live Photos), all from signals the scan already reads plus one cheap measure on the grey
image Blurry already builds. Bursts leave Similar. Trims and removals share one confirmation sheet
and one PhotoKit change block; a trimmed Live Photo becomes a new still that inherits the
original's analysis so the next scan does not meet a stranger. Decisions are in
[research.md](research.md); types in [data-model.md](data-model.md); checks in
[quickstart.md](quickstart.md).

## Technical Context

**Language/Version**: Swift 6, Xcode 26 (project generated by xcodegen from `project.yml`)

**Primary Dependencies**: PhotoKit, Vision, SwiftUI, SwiftData. No new third-party dependency.

**Storage**: the existing SwiftData store (`Packages/CleanupKit/Sources/CleanupKit/Store`), new
optional columns on `LibraryItemRecord`, one field on `StoreMetaRecord`; results snapshot in
`StateRecord` as today.

**Testing**: `swift test` on CleanupKit (unit, accuracy, host tests with fake libraries); XCUITest
flows on the iPhone 17 simulator against `DemoPhotoLibrary`; `BaselineKit` run on a device;
`ScaleBench` on the Mac; `scripts/check-no-network.sh`.

**Target Platform**: iOS 26 and macOS 26, as 013. Nothing here needs a newer API than the project
already uses (burst selection types, paired video resources and screen-recording subtype are
long-standing PhotoKit).

**Project Type**: mobile and desktop app over a Swift package.

**Performance Goals**: 30,000-item build within 5% of 011's numbers (SC-003); no new preview
decodes; the metadata refresh for older stores reads only asset properties.

**Constraints**: offline, no network (constitution II); no video frame opened in the free app
(004 FR-004a); nothing removed or written without the one confirmation (001 FR-012); trims only
from a full-quality still already on the device (001 FR-014).

**Scale/Scope**: libraries up to 30,000 items (008); four categories, one new action, one new
sheet section, one new keeper rule, one new metadata refresh.

## Constitution Check

*GATE: passed before Phase 0; re-checked after Phase 1 design, still passing.*

- **I. Local-only data**: new fields live in the existing on-device store; the new still is
  written to the person's own Photos library on the device. Pass.
- **II. No outbound network**: resource reads use `NetworkOffOptions`; `PHAssetCreationRequest`
  is a local write; no new endpoint, SDK or flag. `check-no-network.sh` stays green. Pass.
- **III. Offline-safe dependencies**: no new dependency. Pass.
- **IV. User owns their data**: removals and trims happen only after the summary sheet and the
  system dialog; the original Live Photo goes to Recently Deleted, recoverable; Delete All Data
  covers the new columns because they are in the same store. Pass.
- **V. Verifiable privacy**: the no-network script and the free-app "no video frame" assertions
  in the baseline run cover the new paths. Pass.
- **Data & Network check**: reads burst picks, shared flag, screen-recording kind and paired-video
  size from the library; computes emptiness from the preview already decoded; writes a new still
  asset and deletes the original on confirmation; stores everything in the local store. Zero
  network access.

## Complexity Tracking

No constitution violations. One design note: the two-pass builder and the `.trim` action are the
only places a single asset may appear in two categories (spec FR-007); `CleanupResults.category(of:)`
keeps returning the removal category, and a new `trimCategory(of:)` answers for Live Photos, so
nothing that reasons about removals changes meaning.

## Risks

- **New-asset identity**: album re-adding needs the album fetch per original; smart albums and
  shared albums are skipped (the latter never listed). A Live Photo in hundreds of albums is fine
  (one change request per album).
- **Confirmation wording**: iOS's own dialog says "delete", not "trim"; the sheet explains it once
  (014 style) and nowhere else.
- **Old stores**: the metadata refresh runs once and reads properties only; on a 30,000-item
  library it is a few seconds, shown as the quick check already is.
- **Dark thresholds**: tuned on synthetic images; real Night mode shots are the open question, as
  Unimportant's weights were in 011 (T030). The flat-extremes guard keeps the pocket case safe
  whatever the structure rule does.
